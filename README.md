# registry

A SPEL program built with [spel-framework](https://github.com/logos-co/spel).

**This project implements [LP-0023 — LEZ Program Registry](LP0023.md).**
Dual-licensed under MIT AND Apache-2.0. The full lifecycle (deploy, register,
search, attributed independent verification, authorization checks) is working
on localnet; see `LP0023.md` for program IDs, PDAs, and tested commands.

> **No Docker on this machine.** `make build` (cargo-risczero) requires Docker;
> use the local-toolchain workflow in `LP0023.md` instead. It builds the guest
> with `cargo +risc0` and wraps the raw ELF in R0BF format with the local
> `make-bin` helper. `make idl`, `make ffi-gen`, and `make ui-gen` all work
> without Docker.

## Prerequisites

- Rust + [risc0 toolchain](https://dev.risczero.com/api/zkvm/install)
- [LSSA wallet CLI](https://github.com/logos-blockchain/lssa) (`wallet` binary)
- A running sequencer

## Quick Start

```bash
# 1. Build the guest binary
make build

# 2. Generate the IDL (auto-extracts from #[lez_program] annotations)
make idl

# 3. Deploy to sequencer
make deploy

# 4. See available commands (auto-generated from your program)
make cli ARGS="--help"

# 5. Run an instruction (spel.toml provides IDL and binary paths)
make cli ARGS="<command> --arg1 value1 --arg2 value2"

# Dry run (no submission):
make cli ARGS="--dry-run -- <command> --arg1 value1"
```

## Registry Browser (read-only host tool)

`registry_browser` enumerates the on-chain global index, derives each entry PDA,
fetches and Borsh-decodes the entries, and filters by name / tag / author /
independent verification. It reads the sequencer connection from `LEE_WALLET_HOME_DIR`.

```bash
source ~/.cargo/env
export RUSTFLAGS='--cfg getrandom_backend="custom"'
export LEE_WALLET_HOME_DIR="$PWD/.scaffold/wallet"
cargo build -p registry-examples --bin registry_browser

./target/debug/registry_browser                    # table of all entries
./target/debug/registry_browser --index-only       # just the global index
./target/debug/registry_browser --name registry    # name substring (case-insensitive)
./target/debug/registry_browser --tag registry     # filter by tag (repeatable)
./target/debug/registry_browser --verified         # only independently verified
./target/debug/registry_browser --author <base58>  # filter by author
./target/debug/registry_browser --json             # full JSON records
```

Verified against localnet: the tool derives the exact known index PDA
(`9mr5hePKo24ZHNztzVpuRND7PeAsR17yQ2M5HHPKcbw3`) and entry PDA, and decodes the
live `RegistryEntry`. Uses `registry_core`'s Borsh types, so host and guest stay
byte-identical.

## Registry JSON API (read-only)

`registry-api` is a small Axum HTTP server exposing the same on-chain data as
`registry_browser`. Both binaries share the fetch/decode/filter helpers in
`registry-api/src/lib.rs`, so host behaviour stays consistent. It never submits
transactions.

```bash
source ~/.cargo/env
export RUSTFLAGS='--cfg getrandom_backend="custom"'
export LEE_WALLET_HOME_DIR="$PWD/.scaffold/wallet"   # sequencer config lives here
make api
# or: cargo run -p registry-api --bin registry-api
```

Configuration (all optional):

| Env var | Default |
|---|---|
| `REGISTRY_API_ADDR` | `127.0.0.1:3030` |
| `LEE_WALLET_HOME_DIR` | `.scaffold/wallet` (relative to the working directory) |
| `REGISTRY_PROGRAM_ID` | final v5 program ID (hex, 64 chars) |

Endpoints (all `GET`, JSON responses; errors are `{"error":"..."}`):

| Endpoint | Description |
|---|---|
| `/health` | `{"status":"ok"}` |
| `/index` | Array of registered program IDs (base58 strings) |
| `/entries` | Array of full decoded `RegistryEntry` objects |
| `/search?name=registry&tag=spel&author=<base58>&verified=true&limit=10` | Filtered entries. `name` is a case-insensitive substring match; tags are OR-matched (also case-insensitive substring, as in `search_entries`); `author`, `verified` and `limit` are optional |
| `/entry/<base58>` | Single entry by program ID; `404` when it is not in the index |

`[u8; 32]` fields in `RegistryEntry` (`program_id`, `author`, `verifier`) are
serialized as JSON arrays of bytes, matching `registry_browser --json`. Invalid
query parameters return `400`; upstream account/decode failures return `502` or
`500` with a JSON error body.

```bash
curl -s http://127.0.0.1:3030/health
curl -s http://127.0.0.1:3030/index
curl -s http://127.0.0.1:3030/search?tag=registry
curl -s 'http://127.0.0.1:3030/search?name=registry&verified=true'
curl -s http://127.0.0.1:3030/entry/6FMaVQ6CmbAVNHgwsmmeBe5kiiKkQRFtqu4GUQ2vAf2T
```

## Logos Storage upload client (QtRO)

The storage module is a Qt Remote Objects source on a Unix socket, not an HTTP
service. `tools/qtro_storage_upload.py` (PySide6 `QtRemoteObjects`) uploads local
files and reports the resulting CIDs. `tools/launch_storage_host.sh` starts an
isolated `logos_host` with a caller-controlled token when the
Basecamp-managed instance's capability token is unavailable to a headless
client.

```bash
# terminal 1: keep this running
tools/launch_storage_host.sh

# terminal 2
python3 tools/qtro_storage_upload.py \
  --token-file /tmp/proclaim_storage_token \
  --init-json '{"data-dir":"/home/xps/proclaim-storage-data","network":"logos.test"}' \
  --host-log <host-stderr-log> \
  --out /tmp/cids.json \
  artifacts/registry-idl.json artifacts/proclaim-source-v5.tar.gz
```

The bridge signature is `callRemoteMethod(authToken, methodName, args)`; only
`getPluginMethods`/`getPluginEvents`/`getPluginInterface` are ungated. PySide6
6.12 does not expose dynamic-replica return values, so `--host-log` is used to
recover CIDs when the `storageUploadDone` event is dropped. See `LP0023.md` for
the CIDs currently recorded on chain.

## How It Works

The `#[lez_program]` macro in your guest binary defines your on-chain program.
The framework automatically:

1. **Generates an `Instruction` enum** from your function signatures
2. **Generates an IDL** (Interface Description Language) describing your program
3. **Provides a full CLI** for building, inspecting, and submitting transactions

You write the program logic. The framework handles the rest.
